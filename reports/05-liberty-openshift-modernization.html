The Jakarta EE 8 monolith (dlis-core, dlis-web, dlis-ear, dlis-cics-bridge) was decomposed into three Liberty microservices that own their data, plus a shared library and an nginx gateway that keeps the public /dlis/api/v1 URL contract. Each service has its own Liberty configuration, container image (multi-arch manifest list) and OpenShift manifests. An Ansible playbook builds, publishes, deploys and verifies them on one or more clusters, x86 first and IBM Z second.

Read this first. Everything was built and unit tested, the manifests were rendered and schema-validated, and one image (amd64) was started locally. Nothing was deployed to a real OpenShift cluster, to OpenShift on IBM Z, or against a real Db2. The s390x image was built as part of a manifest list but never started. The Ansible apply, rollback, image-push and verify logic is untested. See Validation.

Decomposition: why three services

Services were cut along data ownership and transactional cohesion, not along Java packages. The monolith used one XA datasource and EJB transactions that spanned several tables, so each cut was tested against the question “would this need a distributed transaction?”

ServiceOwns tablesResponsibilityReason for the boundary
dlis-candidate-serviceCANDIDATERegistration and lookup of candidates (PII)PII is isolated: tighter access, audit and network policy; read-mostly, scales on its own
dlis-licensing-serviceLICENSE_APPLICATION, DRIVING_HISTORY, ISSUED_LICENSE, AUTHORITY_USERApplication, eligibility, history check, approvals 1 and 2, issuanceEligibility, history, approval and issue update one application aggregate in sequence; splitting them would need distributed transactions
dlis-payment-servicePAYMENT, LICENSE_FEE_SCHEDULEFee calculation and payment recordingDifferent change cadence and compliance scope (money); a clean seam through a single “payment recorded” event

Considered and rejected: one service per workflow step (5+ services) would split a single transactional aggregate and produce chatty synchronous calls; keeping a single service would give no independent scaling or PII isolation. Three is the smallest count that gives separate data ownership for the sensitive and the financial data without distributed transactions on the hot path.

The CICS programs (CAND, APPL, PAAP) call the services in-JVM, so the bridge stays on z/OS together with the legacy modules. They are the strangler / rollback path and were not modified.

Architecture

Client ──TLS──► OpenShift Route (edge) ──► dlis-gateway (nginx, unprivileged)
                                              │ /dlis/api/v1/candidates                      ──► dlis-candidate-service ──► CANDIDATE
                                              │ /dlis/api/v1/applications/{id}/payment        ──► dlis-payment-service   ──► PAYMENT, LICENSE_FEE_SCHEDULE
                                              │ /dlis/api/v1/applications[/...]              ──► dlis-licensing-service ──► LICENSE_APPLICATION, DRIVING_HISTORY,
                                              │                                                                            ISSUED_LICENSE, AUTHORITY_USER
                                              └ any other path / payment-recorded            ──► 404

licensing ──REST (CandidateGateway)───────► candidate   (date of birth + active flag only)
payment   ──REST (ApplicationGateway)─────► licensing   (read application; POST payment-recorded = saga step)
All three ──JDBC (non-XA, own datasource, authData)──► Db2 schema DLIS (shared schema, no cross-service foreign keys)

Cross-service behaviour

  • Payment saga: payment reads the application from licensing, records the payment, then calls payment-recorded on licensing. The callback is idempotent per paymentReference.
  • Failure handling: a business rejection from licensing marks the payment transaction rollback-only; an unreachable service raises RemoteServiceException (rollback, HTTP 503).
  • Security: Liberty appSecurity-3.0 with the existing roles plus a new DLIS_SERVICE role (group DlisServices) for service-to-service calls. TLS ends at the Route, so the CONFIDENTIAL transport guarantee was removed from the services’ web.xml. Db2 credentials use authData.
  • Observability: mpHealth-3.1 (/health/live, /health/ready checks the database) and mpMetrics-3.0.

Kubernetes objects per cluster: Namespace, ServiceAccount, ConfigMap, Secrets (Db2, service account, registry, optional Db2 truststore and pull secret), 3 service Deployments + Services, gateway Deployment + Service, HPA and PDB per Deployment, NetworkPolicies (default-deny ingress; allow router → gateway, gateway → services, licensing → candidate, payment → licensing, monitoring; no egress policy), Route (edge TLS).

Performed Steps

  1. 1. Branch and baseline
    Created liberty-openshift-modernization from upgrade-to-java-17 (Java 17 is required by the Liberty java17 images). Baseline build: 187 tests in dlis-core, 25 in dlis-cics-bridge, all passing.
  2. 2. Analysis and decomposition
    Mapped tables, EJB transaction boundaries, REST resources and the CICS programs; chose the three-service split above.
  3. 3. Shared library dlis-service-commons
    ServiceResult, ApiErrors, REST client helpers, RemoteServiceException + mapper, liveness and database readiness checks.
  4. 4. Three Liberty services
    Ported domain, DAOs, EJBs and JAX-RS resources into dlis-candidate-service, dlis-licensing-service, dlis-payment-service. Added CandidateGateway, ApplicationGateway, the payment saga and the payment-recorded callback. Per-service server.xml, web.xml, jvm.options, Dockerfile and split DDL (DLIS-*-TABLES.sql, no cross-service foreign keys). Tests were ported and extended.
  5. 5. Parent POM
    Added the four modules and the managed dependencies (MicroProfile Health 3.1; Jersey 2.41 and jakarta.json 1.1.6 for tests).
  6. 6. Images
    Wrote the Dockerfiles. Built the candidate image for amd64 and started it with podman; built a two-architecture manifest list. Per request, image building was not pursued further.
  7. 7. OpenShift manifests
    Jinja2 templates for all objects listed above, including the nginx gateway configuration (tested locally with nginx).
  8. 8. Ansible pipeline
    Playbooks site.yml, rollback.yml, render.yml, six roles, an example inventory with an x86 and a Z cluster. Fixed two bugs found while rendering (a colon in a task name, a recursive checksum variable).
  9. 9. Lint and review fixes
    Reached ansible-lint production profile with zero findings; named the rollout block; removed a masking failed_when: false and a redundant when on the manifest assertion; replicas are now pinned only when a Deployment is first created so that the HPA owns the count afterwards.
  10. 10. Documentation and housekeeping
    deploy/ansible/README.md, a section in the root README.md, .gitignore entries for deploy/.rendered/ and for the two lint configuration dotfiles.
  11. 11. Final verification
    mvn clean install on the whole reactor, Ansible syntax checks, offline rendering of both clusters and schema validation of the output.

Risks and recommended next steps

  • Run render.yml (offline), then site.yml --tags deploy,verify against a non-production x86 cluster first; then the Z cluster. Fix whatever the first live run reveals.
  • db2jcc4.jar is staged by Maven from the dependency declared in the service POMs; confirm that the driver version suits both Db2 LUW and Db2 for z/OS in your build environment.
  • The demo basicRegistry users should be replaced by LDAP (or SAF on Z) before production.
  • Services share one Db2 schema with the legacy modules; ownership is by convention, not enforced by grants. Create per-service Db2 users with table-level grants.
  • The payment saga is synchronous with a compensating rollback only on the payment side; add a retry/outbox if licensing downtime must not fail payments.
  • Cut over traffic gradually (Route weights or the gateway) and keep the monolith and CICS bridge until the services are proven.
  • Keep the vault file encrypted; inventories/example/.../vault.yml contains dummy values only.
